# 第十二章（通俗版）：召回信息合并——把散装零件组装成图纸

---

## 一、为什么召回结果不能直接丢给大模型？

三路召回拿到的信息是**分散的**：

- 字段召回：`fact_order.order_amount`、`dim_region.region_name`
- 指标召回：`GMV`、`AOV`
- 取值召回：`dim_region.region_name.华北`

但大模型生成 SQL 时，更希望看到的是**按表组织的结构**：

```yaml
- 表名: fact_order
  角色: 事实表
  字段:
    - order_amount: decimal, 度量值, 订单金额

- 表名: dim_region
  角色: 维度表
  字段:
    - region_name: string, 维度, 示例值["华北"]
```

> 打个比方：你给一个人几个零件（order_amount、GMV、华北），他还是不知道怎么组装。你得给他一张按部件分好的图纸。

**`merge_retrieved_info` 就是做这件事：把散装零件整理成图纸。**

---

## 二、合并后的目标结构

合并节点最终返回两个字段：

| 字段 | 是什么 | 后续谁用 |
|------|--------|---------|
| `table_infos` | 按表组织的字段信息 | 过滤表、生成 SQL |
| `metric_infos` | 整理后的指标定义 | 过滤指标、生成 SQL |

### table_infos：按表分组

```python
[
    {
        "name": "fact_order",
        "role": "fact",
        "description": "订单事实表",
        "columns": [
            {"name": "order_amount", "type": "decimal", "role": "measure", ...}
        ]
    }
]
```

### metric_infos：指标定义

```python
[
    {
        "name": "GMV",
        "description": "成交金额总和",
        "relevant_columns": ["fact_order.order_amount"],
        "alias": ["成交额", "交易额", "销售总额"]
    }
]
```

## 三、合并主线：五步走

```text
1. 把字段列表转成 Map（column_id → ColumnInfo），方便按 ID 查找
2. 把指标依赖的字段补进字段列表（指标被召回 → 它依赖的字段也必须有）
3. 把字段取值补进字段的 examples（"华北" → region_name 的示例值）
4. 按 table_id 对字段分组，组装 TableInfoState
5. 把 MetricInfo 转成 MetricInfoState
```

### 第一步：字段列表 → Map

```python
column_map = {col.id: col for col in retrieved_column_infos}
```

好处：后面判断"某个字段是否已存在"只需 O(1)，不用遍历列表。

### 第二步：补齐指标依赖字段

如果召回了 GMV 指标，它依赖 `fact_order.order_amount`。这个字段可能在字段召回里已经有了，也可能没有。没有的话，要去 Meta MySQL 查出来补上。

**原则：只要某个指标被召回，它依赖的字段也必须进入上下文。**

### 第三步：补齐字段取值

取值召回得到的是"某个字段里存在某个值"，比如 `region_name` 里存在"华北"。

合并节点要把这个值追加到对应字段的 `examples` 中，这样生成 SQL 时模型就知道 `WHERE region_name = '华北'` 是对的。

### 第四步：按表分组

把字段按 `table_id` 分组，每张表带上自己的字段列表，组装成 `TableInfoState`。

### 第五步：转换指标

`MetricInfo` → `MetricInfoState`，去掉内部 id，只保留 SQL 生成需要的信息。

---

## 四、State 更新

合并后，State 多了两个关键字段：

```python
class DataAgentState(TypedDict):
    # ... 之前的字段 ...
    table_infos: list[TableInfoState]    # 合并后的表结构上下文
    metric_infos: list[MetricInfoState]  # 合并后的指标上下文
```

---

## 五、Context 更新

合并节点需要查 Meta MySQL 补齐信息，所以 Context 加入了 `meta_mysql_repository`。

---

## 六、本章要点速记

| 要点 | 一句话 |
|------|--------|
| 合并的目的 | 把分散的召回结果整理成大模型能用的上下文 |
| 补齐 | 指标依赖的字段、字段取值，缺了就从 Meta MySQL 查 |
| 分组 | 按 table_id 把字段归到各张表 |
| table_infos | 按表组织的字段信息，后续生成 SQL 的核心输入 |
| metric_infos | 整理后的指标定义，去掉内部 id |
| 不调大模型 | 合并节点只做数据整理，不调模型 |
