## 一、联调时还会遇到什么问题？

接口跑通了，但真正联调时还有三个问题：

1. **节点失败后，后续节点还要不要执行？** → 不应该继续
2. **前端怎么知道每一步是成功还是失败？** → 需要统一消息协议
3. **多个请求并发时，日志怎么区分？** → 需要 request_id

---

## 二、统一 SSE 消息协议

前端要稳定渲染，后端返回的数据结构不能随意变化。约定三类消息：

### progress：节点进度

```json
{"type": "progress", "step": "抽取关键词", "status": "running"}
{"type": "progress", "step": "抽取关键词", "status": "success"}
{"type": "progress", "step": "抽取关键词", "status": "error"}
```

前端根据 status 展示不同状态：执行中 / 已完成 / 已失败。

### result：最终查询结果

```json
{"type": "result", "data": [{"region_name": "华北", "amount": 41099.5}]}
```

### error：全局错误

```json
{"type": "error", "message": "division by zero"}
```

### progress.error 和 type.error 的区别

| | progress.status=error | type=error |
|--|----------------------|-----------|
| 告诉前端什么 | **哪一步**失败了 | **为什么**失败 |
| 前端怎么用 | 标红该步骤 | 展示错误详情 |

**一个管界面状态，一个管错误详情。**

## 三、节点异常处理：失败后必须停止

### 推荐写法

```python
async def extract_keywords(state, runtime):
    step = "抽取关键词"
    writer = runtime.stream_writer

    writer({"type": "progress", "step": step, "status": "running"})

    try:
        # 业务逻辑
        keywords = extract(query)
        writer({"type": "progress", "step": step, "status": "success"})
        return {"keywords": keywords}
    except Exception as e:
        logger.error(f"{step} failed: {e}")
        writer({"type": "progress", "step": step, "status": "error"})
        raise  # 关键：继续抛出异常，中断图执行
```

**核心：捕获异常后，还要 `raise`。** 如果不 raise，LangGraph 会认为节点正常完成，继续执行后续节点。

### validate_sql 是特殊节点

它的 EXPLAIN 失败不代表"节点失败"，而是"SQL 需要校正"。所以它不 raise，而是把错误写入 State，交给条件边判断。

> 系统异常要中断，业务分支要进入图的条件流转。

### run_sql 输出最终 result

```python
writer({"type": "progress", "step": "执行SQL", "status": "success"})
writer({"type": "result", "data": result})  # 最终查询结果
```

## 四、QueryService：统一序列化和兜底

节点通过 `writer(...)` 写出的是 Python 字典，SSE 要的是文本。QueryService 负责转换：

```text
节点 writer(dict) → graph.astream 产出 chunk → json.dumps → data: ...\n\n → 前端
```

两个关键参数：

| 参数 | 作用 |
|------|------|
| `ensure_ascii=False` | 保留中文，不转 Unicode |
| `default=str` | Decimal、日期等类型兜底转字符串 |

异常兜底：

```python
except Exception as e:
    error = {"type": "error", "message": str(e)}
    yield f"data: {json.dumps(error, ensure_ascii=False, default=str)}\n\n"
```

## 六、request_id：让并发日志能查得清楚

### 问题

多个请求并发时，日志会交错：

```text
抽取关键词成功
召回字段信息成功
抽取关键词成功    ← 这是哪个请求的？
生成SQL
```

没有标识，分不清哪行日志属于哪个请求。

### 解决方案：中间件生成 request_id

```python
@app.middleware("http")
async def add_request_id(request, call_next):
    request_id = uuid.uuid4()
    request_id_ctx_var.set(request_id)  # 写入 ContextVar
    response = await call_next(request)
    return response
```

### ContextVar：并发安全的上下文变量

普通全局变量：所有请求共用一份值，并发时会互相覆盖。

ContextVar：每个异步上下文各自保存一份值，请求 A 的 request_id 不会覆盖请求 B 的。

> 如果有 Java 经验，ContextVar 类似 ThreadLocal。

```python
from contextvars import ContextVar
request_id_ctx_var: ContextVar[str] = ContextVar("request_id", default="1")
```

默认值 `"1"` 是给命令行脚本用的——脚本不经过中间件，没人 set request_id。

### loguru 自动注入 request_id

```python
def inject_request_id(record):
    request_id = request_id_ctx_var.get()
    record["extra"]["request_id"] = request_id

logger = logger.patch(inject_request_id)
```

业务代码只写 `logger.info("抽取关键词成功")`，输出自动带上 `request_id`。

## 七、项目总结

到这一章为止，问数智能体形成了完整闭环：

| 层次 | 做什么 |
|------|--------|
| 数据层 | MySQL 元数据库 + 数仓 + 配置 |
| 检索层 | Qdrant 向量检索 + ES 全文检索 |
| 智能体层 | LangGraph 工作流（抽取→召回→合并→过滤→SQL闭环） |
| 服务层 | QueryService 组装 State/Context |
| API 层 | FastAPI + SSE 流式响应 |
| 可观测层 | 异常协议 + request_id + loguru |

### 五个值得记住的工程经验

1. **不要让大模型凭空生成 SQL**——先整理好上下文
2. **节点职责要清晰**——每个节点只做一件事
3. **状态数据和运行时工具要分开**——State vs Context
4. **接口交付要考虑用户体验**——SSE 流式返回进度
5. **异常和日志不是最后才补的**——节点失败要中断，日志要能追踪
