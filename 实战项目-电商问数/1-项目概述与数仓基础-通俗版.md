# 第一章（通俗版）：项目是干嘛的？数仓又是啥？

---

## 一、这个项目到底要解决什么问题？

想象一下这个场景：

你是公司的运营同学，你想知道"华北地区的销售总额是多少"。

传统做法：找数据分析师 → 等他写 SQL → 等他跑查询 → 拿到结果。快的话半天，慢的话排期一周。

**「电商问数」要做的就是：让你直接用自然语言提问，系统自动帮你查。**

这就是所谓的 **NL2SQL**（Natural Language to SQL）——把"人能看懂的话"翻译成"数据库能执行的 SQL"。

---

## 二、为什么不直接查业务数据库？

你可能会想：数据不是已经在数据库里了吗？直接查不就行了？

问题在于，**业务数据库和分析查询的目标不一样**：

| | 业务数据库 | 数据仓库 |
|--|-----------|---------|
| **主要任务** | 让业务跑起来（下单、支付、查订单） | 让数据分析跑起来（统计、对比、趋势） |
| **查询特点** | 一次查一条，要快 | 一次扫一堆，要算 |
| **设计重点** | 写入快、响应快 | 方便统计、方便分组 |

如果把分析 SQL 直接跑在业务数据库上，可能会让线上系统变慢，甚至影响正常下单。

**所以企业通常会把数据同步到一个专门用于分析的系统——这就是"数据仓库"。**

> 打个比方：业务数据库像"柜台"，要快速处理每笔交易；数据仓库像"档案室"，专门用来翻历史、做统计。

本项目用 MySQL 来模拟数据仓库（真实企业可能用 Hive 等大数据工具，但核心思路一样）。

## 三、数仓里的表长什么样？——事实表和维度表

数据仓库里最常见的建模方式叫**维度建模**。它的核心思想很简单：

> 把表分成两类：**事实表**（记录"发生了什么"）和**维度表**（描述"在什么条件下发生的"）。

### 3.1 事实表：记录"发生了什么事"

本项目的事实表叫 `fact_order`，每一行就是一笔订单：

| 字段 | 含义 | 角色 |
|------|------|------|
| order_id | 订单编号 | 主键 |
| customer_id | 哪个客户下的单 | 外键 → 关联客户表 |
| product_id | 买的什么商品 | 外键 → 关联商品表 |
| region_id | 发往哪个地区 | 外键 → 关联地区表 |
| date_id | 什么时候下的单 | 外键 → 关联日期表 |
| order_quantity | 买了多少件 | **度量值**（可以统计的数字） |
| order_amount | 花了多少钱 | **度量值**（可以统计的数字） |

**事实表的特点：一个主键 + 一堆外键 + 一堆度量值。**

### 3.2 维度表：描述"从哪些角度看这件事"

维度表是事实表的"补充说明"。本项目有四张维度表：

| 维度表 | 描述什么 | 关键字段 |
|--------|---------|---------|
| dim_customer | 客户信息 | 姓名、性别、会员等级 |
| dim_product | 商品信息 | 商品名、品类、品牌 |
| dim_region | 地区信息 | 省份、大区、国家 |
| dim_date | 时间信息 | 年、季度、月、日 |

**维度表的特点：一个主键 + 一堆描述字段。**

### 3.3 它们怎么配合？

想象你要回答"华北地区的销售总额"：

1. **事实表** `fact_order` 提供了"金额"（order_amount）
2. **维度表** `dim_region` 提供了"地区"（region_name = "华北"）
3. 通过 `region_id` 把两张表连起来
4. 筛选 + 求和 → 得到答案

```text
fact_order（金额数据）
    ↕ 通过 region_id 关联
dim_region（地区信息）
```

## 四、用三个问题理解事实表和维度表

| 问题 | 事实表 | 维度表 | 怎么连 | 统计什么 | 怎么算 |
|------|--------|--------|--------|---------|--------|
| 各地区销售总额 | fact_order | dim_region | region_id | order_amount | sum |
| 各品牌销售总额 | fact_order | dim_product | product_id | order_amount | sum |
| 男性用户订单总额 | fact_order | dim_customer | customer_id | order_amount | sum |

规律很明显：

1. 先找到事实表（承载核心数值）
2. 再根据分析维度关联对应的维度表
3. 最后做筛选、分组、聚合

## 五、指标是什么？

你可能注意到了，用户说的"销售总额"并不直接对应某个字段名。它更像一个**业务指标**：

- 指标名：GMV（Gross Merchandise Value）
- 指标含义：所有订单金额的总和
- 依赖字段：`fact_order.order_amount`
- 别名：成交额、交易额、销售总额

**指标不是数据库里天然存在的字段，而是业务上定义的"计算口径"。** 这也是为什么后面系统需要单独维护指标信息——大模型光看字段名，不知道"销售总额"等于"GMV"等于"sum(order_amount)"。

## 六、本章要点速记

| 概念 | 一句话 |
|------|--------|
| NL2SQL | 把自然语言翻译成 SQL |
| 业务数据库 | 支撑日常业务运行，强调快 |
| 数据仓库 | 支撑统计分析，强调方便算 |
| 事实表 | 记录"发生了什么事"（主键 + 外键 + 度量值） |
| 维度表 | 描述"从哪些角度看"（主键 + 描述字段） |
| 指标 | 业务上定义的计算口径，如 GMV = sum(order_amount) |

**记住这句话就够了：事实表负责记录业务事件，维度表负责补充观察角度，指标负责定义"怎么算"。**
