# 第十章（通俗版）：问数智能体——把流水线搭起来

---

## 一、知识库建好了，然后呢？

前面几章把元数据知识库搭好了。系统现在知道有哪些表、哪些字段、字段是什么意思、有哪些真实取值。

但知识库不会自动回答用户问题。用户输入"统计华北地区的销售总额"，系统至少要判断：

- "华北地区"是不是某个字段的真实取值？
- "销售总额"更像字段还是业务指标？
- 应该查哪张表？需要关联哪些维度表？
- 生成的 SQL 对不对？能不能执行？

**所以问数智能体不是简单地把问题丢给大模型，而是一条多步骤的工作流。**

---

## 二、整条工作流长什么样？

```text
用户问题
  → 抽取关键词
  → 三路并行召回（字段 / 指标 / 字段取值）
  → 合并召回信息
  → 过滤表 / 过滤指标
  → 补充额外上下文
  → 生成 SQL
  → 校验 SQL
  → 校验通过 → 执行 SQL
  → 校验失败 → 校正 SQL → 再执行
```

### 三个关键设计

1. **三路召回可以并行**——字段、指标、取值都依赖关键词，但彼此没有先后顺序
2. **召回后要合并过滤**——召回宁可多，生成 SQL 要精
3. **SQL 生成后要校验**——大模型可能写错字段名、表名、join 条件

## 三、LangGraph 五件套

问数智能体用 LangGraph 编排，先搞清楚五个核心概念：

| 概念 | 通俗理解 | 在项目里做什么 |
|------|---------|--------------|
| **StateGraph** | 流水线的图纸 | 定义整条工作流的结构 |
| **State** | 流水线上传递的数据 | 节点之间共享的业务数据 |
| **Node** | 流水线上的工位 | 每个工位做一件事 |
| **Edge** | 工位之间的传送带 | 决定下一步去哪 |
| **Runtime Context** | 工位上的工具箱 | 运行时依赖（数据库连接、客户端等） |

> 记住一句话：Graph 管结构，State 管数据，Node 做处理，Edge 管流转，Runtime 放工具。

---

## 四、State：共享状态

State 是整张图运行时共享的数据。每个节点读取 State，返回自己要更新的部分。

```python
class DataAgentState(TypedDict):
    query: str                    # 用户问题
    keywords: list[str]           # 抽取的关键词
    retrieved_column_infos: list  # 字段召回结果
    retrieved_metric_infos: list  # 指标召回结果
    retrieved_value_infos: list   # 字段取值召回结果
    table_infos: list             # 合并后的表结构上下文
    metric_infos: list            # 合并后的指标上下文
    sql: str                      # 生成的 SQL
    error: str                    # SQL 校验错误
```

**判断数据该不该放进 State：后续节点还要用、需要被观测、需要参与分支判断的 → 放进 State。只在当前函数临时用的 → 不放。**

---

## 五、Node：每个节点只做一件事

节点函数一般长这样：

```python
async def extract_keywords(state, runtime):
    # 读取 state
    # 用 runtime.context 里的工具做事
    # 必要时用 runtime.stream_writer 输出进度
    # 返回局部状态更新
    return {"keywords": keywords}
```

**节点应该返回 Partial State（只返回自己改的那部分），不要返回整份 State。**

每个节点只做一件事：

| 节点 | 只做什么 |
|------|---------|
| extract_keywords | 只抽关键词 |
| recall_column | 只召回字段 |
| merge_retrieved_info | 只合并召回信息 |
| validate_sql | 只校验 SQL 并写入 error |
| run_sql | 只执行 SQL |

## 六、Edge：普通边和条件边

### 普通边：固定顺序

```python
graph_builder.add_edge("add_extra_context", "generate_sql")
```

表示：补充上下文 → 生成 SQL，顺序固定。

### 条件边：运行时分支

```python
graph_builder.add_conditional_edges(
    source="validate_sql",
    path=lambda state: "run_sql" if state["error"] is None else "correct_sql",
)
```

表示：
- 校验通过 → 执行 SQL
- 校验失败 → 校正 SQL

### 并行边

```python
graph_builder.add_edge("extract_keywords", "recall_column")
graph_builder.add_edge("extract_keywords", "recall_value")
graph_builder.add_edge("extract_keywords", "recall_metric")
```

表示：关键词抽取完成后，三路召回可以同时开始。

---

## 七、Runtime Context：工具和状态要分开

后续节点要用数据库连接、向量检索仓储等对象。这些不是业务状态，而是运行时工具。

```text
业务中间结果 → State
运行时依赖   → Runtime Context
```

不要把 Repository、Client 塞进 State。它们是节点执行时要用的工具，放在 Context 里。

---

## 八、Streaming：让前端看到执行进度

`invoke()` 是"等整张图跑完再拿结果"，`astream()` 是"边执行边看发生了什么"。

项目用 `stream_mode="custom"`，节点内部通过 `writer("抽取关键词")` 输出进度，前端实时看到每一步在做什么。

## 十、本章要点速记

| 要点 | 一句话 |
|------|--------|
| 工作流 | 不是"一个提示词直接生成 SQL"，而是多节点流水线 |
| State | 节点之间共享的业务数据 |
| Node | 每个节点只做一件事，返回局部更新 |
| Edge | 普通边管固定顺序，条件边管运行时分支 |
| Runtime Context | 运行时工具（数据库连接等），不放 State |
| Streaming | 让前端实时看到执行进度 |
| compile() | 把图纸变成可运行的图 |
