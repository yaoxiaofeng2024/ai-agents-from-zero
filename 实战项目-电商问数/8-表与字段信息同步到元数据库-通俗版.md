# 第八章（通俗版）：表和字段信息——先让系统"认识"数仓

---

## 一、这一章在做什么？

上一章搭好了入口，这一章正式落地第一条业务链路：**把配置文件里描述的表和字段，写入 Meta MySQL。**

只有表信息和字段信息先稳定落下来，后面的向量索引、全文索引、SQL 生成才有可靠的基础。

---

## 二、整条链路一览

```text
配置文件描述表和字段
  → 构造业务实体（TableInfo、ColumnInfo）
    → 去数仓补齐真实信息（字段类型、示例值）
      → 通过 Mapper 转成 ORM 模型
        → 事务方式写入 Meta MySQL
```

---

## 三、第一步：配置 → 业务实体

配置文件不是直接入库的，它会先被转换成业务实体。

### 配置里有什么？

```yaml
tables:
  - name: dim_region
    role: dim
    description: 地区维度表
    columns:
      - name: region_name
        role: dimension
        description: 大区名称
        alias: [地区, 区域, 大区]
        sync: true
```

配置主要提供**业务语义**：表角色、字段角色、字段说明、别名。

### 业务实体长什么样？

```python
@dataclass
class TableInfo:
    id: str           # 表名
    name: str
    role: str         # fact 或 dim
    description: str

@dataclass
class ColumnInfo:
    id: str           # "表名.字段名"，如 "fact_order.order_amount"
    name: str
    type: str         # 来自数仓查询，不是配置里写的
    role: str
    examples: list    # 来自数仓查询，不是配置里写的
    description: str
    alias: list[str]
    table_id: str
```

### 为什么字段 ID 要用"表名.字段名"？

因为很多表都有同名字段（如 `id`、`customer_id`）。只用字段名会冲突，加上表名才能保证唯一。

比如：`fact_order.order_amount` 和 `dim_customer.customer_id`。

### 为什么 type 和 examples 不写在配置里？

**能自动获取的信息，就不要让人手工维护。**

- 字段类型 → 数据库表结构里就有，程序自动查
- 示例值 → 真实数据里就有，程序自动取

配置只管"业务语义"（这个字段是什么意思），程序负责补齐"真实结构"（这个字段是什么类型、有哪些值）。

---

## 四、第二步：去数仓补齐真实信息

`DWMySQLRepository` 负责查询数仓：

| 方法 | 做什么 | SQL |
|------|--------|-----|
| `get_column_types(table_name)` | 查一张表所有字段的类型 | `SHOW COLUMNS FROM 表名` |
| `get_column_values(table, column, limit)` | 查某个字段的去重取值 | `SELECT DISTINCT 字段 FROM 表名 LIMIT 10` |

### 为什么字段类型按表查，示例值按字段查？

- 字段类型：一张表查一次就够了（`SHOW COLUMNS` 返回所有字段）
- 示例值：每个字段要单独查（`SELECT DISTINCT` 一次只查一个字段）

---

## 五、第三步：Service 处理业务实体，不直接操作 ORM

Service 层先构造 `TableInfo` 和 `ColumnInfo`，不直接构造 ORM 模型。

**为什么？解耦。**

同一批 `ColumnInfo` 后续还要被拿去写 Qdrant、写 ES。如果 Service 直接绑定 ORM 模型，到处都要带着 ORM 对象跑，会很乱。

---

## 六、第四步：Repository + Mapper 落库

### Mapper 做什么？

```text
TableInfo → TableInfoMapper → TableInfoMySQL（ORM 模型）
ColumnInfo → ColumnInfoMapper → ColumnInfoMySQL（ORM 模型）
```

Mapper 就是翻译器：把业务实体转成 ORM 模型。

### Repository 做什么？

```python
async def save_table_infos(self, table_infos):
    models = [TableInfoMapper.to_model(t) for t in table_infos]
    self.session.add_all(models)
```

Repository 对外接收的是业务实体，内部通过 Mapper 转换后再落库。

### add_all() ≠ 真正写入数据库

`session.add_all()` 只是把对象加入 Session，告诉 ORM "这些需要持久化"。**真正的写入要等事务提交。**

---

## 七、第五步：事务在 Service 层管理

```python
async with self.meta_mysql_repository.session.begin():
    await self.meta_mysql_repository.save_table_infos(table_infos)
    await self.meta_mysql_repository.save_column_infos(column_infos)
```

**为什么事务放在 Service 层？**

- "保存表信息"和"保存字段信息"是同一批业务操作
- 要么一起成功，要么一起失败
- Repository 只管"怎么写"，Service 管"这些写操作怎么组织"

`session.begin()` 的好处：
- 成功 → 自动提交
- 异常 → 自动回滚

---

## 八、整条链路回顾

```text
1. 读取 meta_config.yaml
2. 遍历每张表 → 构造 TableInfo
3. 查数仓 → 拿到字段类型
4. 遍历每个字段 → 查数仓拿示例值 → 构造 ColumnInfo
5. 开启事务
6. Mapper 转换 → ORM 模型 → add_all()
7. 事务提交 → 数据真正写入 Meta MySQL
```

**一句话：配置描述先变成业务实体，业务实体再补齐真实结构与样本，最后以事务方式落到元数据库。**

---

## 九、验证效果

运行脚本后，重点检查 `column_info` 表：

- `id` 是否是"表名.字段名"格式
- `type` 是否有真实字段类型（不是空的）
- `examples` 是否有真实示例值

**只要 type 和 examples 有值，就说明"配置 + 动态补齐 + 落库"链路跑通了。**
