# 第七章（通俗版）：元数据知识库——先编好"说明书"

---

## 一、为什么必须先建元数据知识库？

问数智能体要生成 SQL，但大模型天生不知道你的数仓里：
- 有哪些表可以查
- 哪些字段代表销售额、地区、会员等级
- 用户说的"华北""黄金会员""成交总额"在库里对应什么

**所以必须先把"数仓里有什么、每个东西是什么意思"整理成一套可检索的知识库。**

> 打个比方：数据仓库是"仓库房"，元数据知识库是"仓库的说明书、索引卡和检索系统"。没有说明书，智能体就是在仓库里瞎找。

---

## 二、一次构建会产出什么？

构建脚本跑完之后，会往三个地方写入数据：

| 存储组件 | 写入什么 | 解决什么问题 |
|---------|---------|------------|
| MySQL 元数据库 | 表信息、字段信息、指标信息、字段与指标关系 | 保存完整的结构化元数据 |
| Qdrant | 字段向量、指标向量 | 支撑语义召回 |
| Elasticsearch | 字段真实取值 | 支撑关键词和值域检索 |

---

## 三、四个关键角色：配置、实体、ORM、Mapper

这是本章最容易晕的地方。先搞清楚这四类东西各自干什么：

| 角色 | 做什么 | 类比 |
|------|--------|------|
| **配置文件** | 告诉系统"这次要处理什么" | 任务清单 |
| **业务实体** | 系统内部统一的数据对象 | 标准件 |
| **ORM 模型** | 对应数据库表的映射对象 | 数据库翻译 |
| **Mapper** | 在实体和 ORM 之间做转换 | 翻译器 |

### 它们怎么协作？

```text
配置文件（meta_config.yaml）
  → 业务实体（TableInfo、ColumnInfo、MetricInfo）
    → Mapper 转换
      → ORM 模型（TableInfoMySQL、ColumnInfoMySQL）
        → 写入 MySQL
```

### 为什么要分这么多层？

- **配置文件**只管"输入什么"，不管"怎么存"
- **业务实体**是系统内部统一表达，后续写 Qdrant、写 ES 都用同一套
- **ORM 模型**只管"怎么映射到数据库表"
- **Mapper**负责在两者之间翻译，让各层互不耦合

> 如果 Service 层直接用 ORM 模型，那写 Qdrant 时也得带着 ORM 对象跑，会很乱。

## 四、配置驱动：不是代码决定同步什么，而是配置决定

**核心思想：脚本负责"怎么做"，配置负责"做哪些"。**

为什么不能直接扫描所有表？

1. **不是所有表都值得同步**——中间表、临时表、废弃表不需要暴露给问数系统
2. **数仓会变化**——新增表时改配置就行，不用改代码
3. **字段取值同步应该可选**——不是每个字段都需要把真实值同步到 ES

配置文件 `meta_config.yaml` 大致长这样：

```yaml
tables:
  - name: dim_region
    role: dim
    description: 地区维度表
    columns:
      - name: region_name
        role: dimension
        description: 大区名称
        alias: [地区, 区域, 大区]
        sync: true    # 这个字段要同步真实取值到 ES
```

## 五、同步脚本只做调度，不堆业务

脚本入口 `build_meta_knowledge.py` 很轻，只做这些事：

```text
初始化客户端 → 创建仓储对象 → 创建服务对象 → 调用 service.build() → 关闭连接
```

真正的业务逻辑在 `MetaKnowledgeService.build()` 里：

```python
async def build(self, config_path):
    # 1. 读取配置
    meta_config = 加载配置(config_path)

    # 2. 处理表和字段
    if meta_config.tables:
        column_infos = await 保存表字段到MySQL(meta_config)
        await 保存字段向量到Qdrant(column_infos)
        await 保存字段取值到ES(meta_config, column_infos)

    # 3. 处理指标
    if meta_config.metrics:
        metric_infos = await 保存指标到MySQL(meta_config)
        await 保存指标向量到Qdrant(metric_infos)
```

**入口只负责调度，复杂逻辑沉淀到服务层。**

## 六、代码分层速查

| 层 | 目录 | 类比 |
|----|------|------|
| scripts | `app/scripts/` | controller（入口） |
| services | `app/services/` | service（业务逻辑） |
| repositories | `app/repositories/` | mapper/dao（数据访问） |
| entities | `app/entities/` | DTO/domain（业务实体） |
| models | `app/models/` | ORM 模型 |
| mappers | `app/repositories/mysql/meta/mappers/` | 翻译器 |

## 七、本章要点速记

| 要点 | 一句话 |
|------|--------|
| 元数据知识库 | 不是某个数据库，而是 MySQL + Qdrant + ES 的协作结果 |
| 四类角色 | 配置管输入，实体管表达，ORM 管映射，Mapper 管翻译 |
| 配置驱动 | 代码管"怎么做"，配置管"做哪些" |
| 脚本只调度 | 入口不堆业务，逻辑沉淀到服务层 |
| 构建顺序 | 先写 MySQL → 再写 Qdrant → 最后写 ES |
