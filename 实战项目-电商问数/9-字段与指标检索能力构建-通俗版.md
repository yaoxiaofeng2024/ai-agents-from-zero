## 先讲个故事：为什么光有"字典"还不够？

想象你在一个巨大的图书馆里。图书管理员给了你一本厚厚的目录，上面写着：

- A区3号书架 → 放的是"订单表"
- 第5列叫 `order_amount`，含义是"订单金额"
- 第8列叫 `member_level`，含义是"会员等级"

这个目录很有用，但它本身解决不了下面这类问题——

有人走进来问："帮我查一下**河北省**的**销售总额**。"

你翻开目录："销售总额"……目录里写的是"订单金额"，这俩是一个意思吗？"河北省"……哦，有个地区表，但里面到底写的是"河北省"还是"河北"？

你看，问题来了：**目录帮你找到了"是哪本书"，但没帮你判断"问的东西到底对不对得上"。**

这就是本章要解决的核心问题。上一章我们只是把表和字段的信息存进了数据库（相当于编好了目录），这一章要更进一步：**让系统能真正"理解"用户的自然语言。**

---

## 一、拆开来看：用户问一个问题，系统要搞定三件事

还是拿"统计河北省销售总额"举例。这句话里其实藏了三类信息：

| 用户说的 | 属于什么类型 | 系统要做什么 |
|---------|------------|------------|
| "销售总额" | **字段语义** | 判断它像哪个字段（order_amount？） |
| "河北省" | **字段真实值** | 确认库里存的到底是"河北"还是"河北省" |
| （如果用户说"GMV"） | **业务指标** | 查出 GMV 的定义和它依赖哪些字段 |

所以本章要做的事不是一件，而是**三条并行的检索链路**：

1. **字段向量索引**：帮系统回答"用户在说哪个字段"
2. **字段值全文索引**：帮系统回答"用户说的这个值在库里到底有没有、怎么写"
3. **指标向量索引**：帮系统回答"GMV、AOV 这些业务术语到底是什么"

这三条链路各自独立构建，但最终一起为后面的 SQL 生成提供上下文。

## 二、本章在整个项目里的位置

别看本章内容多，它在工程上只是元数据知识库构建流程的一个环节。

入口文件还是 `build_meta_knowledge.py`，执行流程大致是：

```text
加载配置文件（meta_config.yaml）
  │
  ├─→ 把表和字段信息写入 Meta MySQL（上一章的事）
  │
  ├─→ 同一批字段 → 拆成语义点 → 向量化 → 写进 Qdrant（字段检索）
  │
  ├─→ 需要同步真实值的字段 → 查数仓 → 写进 Elasticsearch（字段值检索）
  │
  └─→ 指标定义 → 写入 Meta MySQL → 向量化 → 写进 Qdrant（指标检索）
```

所以本章并不是新建了一个独立系统，而是把上一章的元数据继续"加工升级"，让它们变成可检索的形式。

## 三、第一部分：字段向量索引 —— 让系统"认字段"

### 3.1 它是干什么的？

简单说：**把每个字段变成一串数字（向量），相似的字段数字也相似，这样用户说"销售额"，系统就能找到"订单金额（order_amount）"。**

### 3.2 怎么做？

核心思路：**一个字段不只建一条记录，而是围着它拆出多个"入口"。**

比如 `order_amount` 这个字段，我们会为它建三个入口：

- 入口1：字段名 → `order_amount`
- 入口2：字段描述 → `订单金额`
- 入口3-5：别名 → `销售额`、`成交金额`、`订单总额`

每个入口都会单独转成一个向量点存到 Qdrant 里。这样不管用户说的是哪个说法，都能命中同一个字段。

> **打个比方**：就像给一本书建索引时，不只按书名建，还按作者名、别名、关键词分别建——确保不管读者怎么查都能找到。

### 3.3 Qdrant 的四个核心概念

这部分可能是最容易懵的地方，先花一分钟搞清楚：

| 概念 | 通俗解释 | 在项目里是什么 |
|------|---------|-------------|
| **Collection** | 一个"集合"，类似数据库的一张表 | `column_info_collection`（字段专用） |
| **Point** | 集合里的一条记录 | 一个字段的一个语义入口 |
| **Vector** | 一串数字，是文本经过 AI 模型编码后的结果 | 把"销售额"这个词变成 `[0.12, -0.08, ...]` |
| **Payload** | 附带在向量旁边的业务数据 | 整个字段的完整信息（字段名、描述、所属表等） |

画成图就是这样：

```text
一个 point = {
    id: "随机ID",
    vector: [0.12, -0.08, 0.33, ...],   ← 用来比较相似度的
    payload: {                            ← 命中后返回给业务用的
        name: "order_amount",
        description: "订单金额",
        table_id: "fact_order",
        ...
    }
}
```

> **一句话记忆**：向量负责"找"，payload 负责"返回有用信息"。

### 3.4 为什么要分批处理？

代码里有两个地方做了分批：

1. **向量化时**：每 20 条文本调一次 AI 模型（避免一次塞太多文本把模型服务打挂）
2. **写入 Qdrant 时**：每 10 条写一次（避免一次写太多把向量库打挂）

两个分批虽然都叫"分批"，但保护的不是同一个东西，分开理解就好。

### 3.5 怎么验证跑通了？

跑完构建脚本后，用一句"销售额"去 Qdrant 里搜，看结果里 `order_amount` 是不是排在前面。能召回就说明链路通了。

```bash
# 在后端项目目录执行
uv run python -m app.scripts.build_meta_knowledge -c conf/meta_config.yaml
```

然后打开 Qdrant Dashboard：http://localhost:6333/dashboard，看看 `column_info_collection` 里有没有数据。

## 四、第二部分：字段值全文索引 —— 让系统"认真实值"

### 4.1 它解决什么问题？

字段向量索引只能回答"销售总额 ≈ order_amount"，但回答不了"库里存的到底是'河北'还是'河北省'"。

如果系统判断错了，生成的 SQL 就会写成：

```sql
WHERE province = '河北省'   -- 错！库里存的是 "河北"
```

SQL 语法完全正确，但结果全是空的——这种 Bug 最难排查。

所以字段值必须单独建一条检索链路，专门回答：**用户说的这个值，在数据库里到底是不是真实存在的？**

### 4.2 怎么做？

分三步走：

**第一步：挑字段。** 不是所有字段都值得建全文索引。只有用户会直接说出口的字段才需要。

```yaml
# 配置文件里用 sync 控制
columns:
  - name: province
    sync: true         # ← 用户会说"河北省"，所以要建
  - name: region_id
    sync: false        # ← 用户不会说"region_id=3"，不用建
```

**第二步：查值。** 从数仓里查出这个字段有哪些真实取值。

```sql
-- 查 dim_region 表的 region_name 列有哪些不同值
SELECT DISTINCT region_name FROM dim_region LIMIT 100000

-- 返回：["华北", "华东", "华南", "西南"]
```

**第三步：写进 Elasticsearch。** 把每个值存成一条文档，用中文分词器建倒排索引。

### 4.3 Elasticsearch mapping 为什么这么设计？

这是字段值能否被正确搜索的关键，只看三个地方：

| 字段 | 类型 | 为什么 |
|------|------|-------|
| `id` | keyword | 只是唯一标识，不需要分词，精确匹配就行 |
| `column_id` | keyword | 精确指向"这个值是哪个字段的"，也不需要分词 |
| `value` | text + ik_max_word 分词器 | **这是真正要搜的字段！** 必须用 text 类型，用中文分词器把"华北地区"切成"华北"+"地区" |

> **记住**：只有 `value` 字段用了 `text` 类型，因为只有它需要被"搜"。`id` 和 `column_id` 更像是标签，用 `keyword` 就够了。

### 4.4 怎么验证跑通了？

打开 Kibana Dev Tools：http://localhost:5601/app/dev_tools#/console/shell

分别执行这三段：

```json
// 1. 看看索引结构对不对
GET value_index/_mapping

// 2. 随便看几条数据
GET value_index/_search
{ "size": 5 }

// 3. 搜一个真实业务词，看能不能命中
GET value_index/_search
{
  "query": {
    "match": { "value": "华北地区" }
  }
}
```

搜"华北地区"能返回结果，且 `column_id` 指向 `dim_region.region_name`，就说明这条链路通了。

## 五、字段的两条检索链路如何配合？

现在把字段的两条链路拼在一起看：

```text
用户问："河北省销售总额"

字段向量索引（Qdrant）
  → "销售总额" ≈ order_amount（字段找到了！）

字段值全文索引（ES）  
  → "河北" 在 dim_region.region_name 里真实存在（值确认了！）

两条链路配合：
  SELECT SUM(order_amount) 
  FROM ... 
  WHERE region_name = '河北'   ← 字段和值都对上了
```

两条链路不是竞争关系，而是**互补关系**：向量索引解决"像哪个字段"，全文索引解决"值对不对"。

## 六、第三部分：指标也要进知识库

### 6.1 为什么指标不能跳过？

假如知识库里只有字段，没有指标，那用户说"看看 GMV"时会发生什么？

系统会一头雾水：GMV 不是任何一个字段名。它需要知道 GMV 的定义、它在业务里怎么算、它和哪些底层字段有关。

所以指标必须单独作为一个知识对象存进去。配置里长这样：

```yaml
metrics:
  - name: GMV
    description: 所有订单的成交金额总和
    relevant_columns:
      - fact_order.order_amount      # ← 关键：标出依赖哪个字段
    alias: [成交总额, 订单总额]
```

注意 `relevant_columns` 这个字段：它把"指标"和"底层字段"桥接起来了。后面系统知道 GMV 依赖 `order_amount`，才能正确生成 SQL。

### 6.2 指标入库做了什么？

指标入库分两步，在同一次数据库事务里完成：

1. **存指标本身**（MetricInfo）：叫什么、定义是什么、别名有哪些
2. **存指标与字段的关系**（ColumnMetric）：GMV 依赖 `fact_order.order_amount`，AOV 依赖 `fact_order.order_quantity`

为什么要拆成两张表？因为指标和字段是**多对多**关系：一个指标可能依赖多个字段，一个字段也可能被多个指标复用。拆开存才能灵活表达这种关系。

### 6.3 指标也要建向量索引

和字段一样，指标也要拆成语义入口：

- 指标名：`GMV`
- 指标描述：`所有订单的成交金额总和`
- 别名：`成交总额`、`订单总额`

每个入口都向量化后写进 Qdrant。但注意：**指标用独立的 collection（`metric_info_collection`）**，不和字段混在一起。因为检索时系统需要区分"我是在找字段还是在找指标"。

## 七、最后：从头到尾跑一遍

所有链路建完之后，做个最终验证：

| 在哪里 | 应该看到什么 |
|--------|------------|
| Meta MySQL | `table_info`、`column_info`、`metric_info`、`column_metric` 表里都有数据 |
| Qdrant Dashboard | 两个 collection：`column_info_collection` 和 `metric_info_collection` |
| Kibana Index Management | `value_index` 索引存在，里面有文档 |

三条链路都确认通了，元数据知识库的构建就基本收口了。

## 八、一句话总结

**这一章的本质：把上一章的元数据继续"加工"，让它们从"只能被程序读取的结构化数据"，变成"能被自然语言检索的知识对象"。**

三条链路分工明确：

```text
字段向量索引（Qdrant）     →  回答"用户在说哪个字段"
字段值全文索引（ES）       →  回答"这个值在库里到底存不存在"
指标向量索引（Qdrant）     →  回答"GMV/AOV 是什么、依赖哪些字段"
```

把这三条链路都建好，后面的 SQL 生成环节才能真正拿到靠谱的上下文。

---

**本章小结（精简版）**

- 一个字段拆多个语义入口，覆盖字段名、描述、别名 → 不同说法都能召回同一个字段
- 字段值单独建全文索引，用中文分词器 → 确认用户在问的值是否真实存在
- 指标独立存储、独立建向量索引 → 让 GMV、AOV 这类业务术语能被系统理解
- 三条链路互补，不是三选一 → 合在一起才构成完整的检索能力
