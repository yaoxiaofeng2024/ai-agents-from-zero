# 第二章（通俗版）：整个系统是怎么跑起来的？

---

## 一、先看全貌：两条主线

整套系统其实就做两件事：

| 主线 | 做什么 | 什么时候做 |
|------|--------|-----------|
| **构建期** | 把数仓里的知识整理成可检索的"知识库" | 提前做，只做一次 |
| **查询期** | 用户提问时，拿知识库去回答问题 | 每次用户提问时做 |

> 打个比方：构建期是"编教材"，查询期是"用教材答题"。没有教材，答题就是瞎蒙。

---

## 二、构建期：先把知识准备好

构建期做的事情，就是把数仓里的表、字段、指标、字段取值整理成一套**可检索的知识库**。

流程如下：

```text
配置文件（告诉系统要同步哪些表和字段）
  → 同步脚本（按配置去数仓取数据）
    → 写入三套存储：
        ├─ MySQL 元数据库：保存结构化元数据（表信息、字段信息、指标信息）
        ├─ Qdrant 向量库：保存字段和指标的语义向量（用于"语义相似"检索）
        └─ Elasticsearch：保存字段真实取值（用于"文本匹配"检索）
```

### 为什么需要三套存储？

| 存储 | 存什么 | 解决什么问题 | 通俗理解 |
|------|--------|------------|---------|
| MySQL 元数据库 | 表名、字段名、指标定义、关系 | 保存最完整的结构化信息 | "权威字典" |
| Qdrant 向量库 | 字段和指标的向量 | 用户换个说法也能找到 | "模糊匹配器" |
| Elasticsearch | 字段的真实取值 | 确认"华北"在库里确实存在 | "值域校验器" |

> 想象一个图书馆：MySQL 是完整的图书目录，Qdrant 是"你说个大概我也能帮你找到"的智能检索，ES 是"确认这本书确实在架上"的库存核对。

---

## 三、查询期：拿知识去回答问题

用户提问后，系统经过这些步骤：

```text
用户提问："统计华北地区的销售总额"
  → 1. 抽取关键词（华北地区、销售总额）
  → 2. 三路并行召回：
       ├─ 字段召回：order_amount、region_name
       ├─ 指标召回：GMV
       └─ 字段值召回：华北
  → 3. 合并召回信息，按表组织
  → 4. 过滤不相关的表和指标
  → 5. 补充额外上下文（如当前日期）
  → 6. 大模型生成 SQL
  → 7. 校验 SQL（语法对不对、字段存不存在）
  → 8. 执行 SQL，返回结果
```

**核心思想：不让大模型"盲写 SQL"，而是先让它拿到经过整理和筛选的上下文。**

## 四、元数据知识库到底是什么？

很多人会混淆"数据仓库"和"元数据知识库"，先搞清楚区别：

| | 数据仓库 | 元数据知识库 |
|--|---------|------------|
| 存的是什么 | 真实数据（订单、商品、客户...） | 关于数据的数据（有哪些表、字段什么意思、指标怎么算...） |
| 类比 | 仓库里的货物 | 仓库的说明书和索引卡 |

**元数据知识库不是某一个数据库，而是 MySQL + Qdrant + Elasticsearch 的协作结果。**

### 元数据库里的四张核心表

| 表名 | 存什么 | 通俗理解 |
|------|--------|---------|
| table_info | 表名、表角色、表说明 | "有哪些表" |
| column_info | 字段名、字段类型、字段角色、字段说明、别名 | "每个字段是什么意思" |
| metric_info | 指标名、指标说明、指标别名、依赖字段 | "业务指标怎么算" |
| column_metric | 字段和指标的关联关系 | "哪个指标用了哪些字段" |

## 五、技术栈速查表

| 模块 | 技术 | 一句话作用 |
|------|------|-----------|
| 数仓 | MySQL | 存真实分析数据 |
| 元数据库 | MySQL | 存结构化元数据 |
| 向量检索 | Qdrant | 语义相似度召回 |
| 全文检索 | Elasticsearch | 字段取值匹配 |
| 向量化 | TEI + bge-large-zh-v1.5 | 文本转向量 |
| 智能体编排 | LangGraph | 把多步骤串成工作流 |
| 后端接口 | FastAPI | 提供 HTTP 服务 |
| 流式返回 | SSE | 实时推送执行进度 |

**一句话总结：构建期用 MySQL + Qdrant + ES + TEI 把知识库建好，查询期由 LangGraph 驱动智能体调用知识，最终生成并执行 SQL。**

## 六、架构图简化版

不用看那些密密麻麻的箭头，记住这两条线就够了：

```text
【构建期】
配置文件 → 同步脚本 → MySQL（结构化）+ Qdrant（向量）+ ES（取值）

【查询期】
用户问题 → 抽关键词 → 三路召回 → 合并过滤 → 生成SQL → 校验 → 执行 → 返回结果
```

**这套系统最关键的设计，不是"大模型会不会写 SQL"，而是"在写 SQL 之前，系统有没有先把正确的上下文准备好"。**
